# Verify an agent receipt, then deliberately break it

Run a real Ed25519 signature check and see tampering fail. No signup, API key, dependency install, or network request is required after cloning. Requires Node.js 18 or newer.

```sh
git clone https://github.com/truthlocks/maip.git
cd maip
node examples/developer-validation/verify.mjs
```

Expected: five `PASS` lines, a fixture hash, and an explicit scope statement. A failed assertion exits nonzero. Read the 30-line verifier before running it.

## What you are verifying

`fixture.json` contains synthetic public data: an agent identifier, action, scopes, metadata, canonical signed bytes, signature and public key. Its bytes were generated by Truthlocks' current `ReceiptSigningBytes` implementation (receipt/v2), then verified by the production `VerifyReceiptSignature` function. The private signing key was generated in memory and discarded. This is **not** a customer record or a hosted platform signing key.

The standalone Node verifier checks those same bytes with Node's cryptography implementation. It then rejects a changed action, corrupted signature and unrelated key, and detects an agent identifier changed in the displayed fields. You can edit `signed_payload.action` in the JSON file: the display-to-payload assertion must fail even if you leave the original signed bytes untouched.

The scope names are signed claims, not permission enforcement by themselves. A signature binds the record to a key; it does not prove the action happened or that its description is true.

## Trust the key separately

The public key bundled here is a trusted input **only for this synthetic test fixture**. For real records, obtain the agent's authorized key from a trusted registry/key-history channel. Never accept a key merely because an untrusted receipt supplies it. An attacker can replace a receipt and its key together. Pin the reviewed Git commit when reproducing these results. This example is not a general-purpose MAIP verifier.

Offline verification cannot establish current revocation status, business identity, authorization, expiry policy or transparency-log inclusion. Check those separately through the hosted API and your application's policy. This is a first-party engineering example, not an independent audit or performance benchmark.

## Try your own agent in the hosted sandbox

1. [Create or open your workspace](https://truthlocks.com/get-started?utm_source=github&utm_medium=developer_walkthrough&utm_campaign=developer_validation_20261018). No payment is needed to inspect this offline demo.
2. In Console, keep the workspace in sandbox and register your own agent. Use [agent registration documentation](https://docs.truthlocks.com/api-reference/machine-identity/agents/register) for the current request body and required scopes.
3. Use [receipt creation](https://docs.truthlocks.com/api-reference/agent-receipts/create) to record a clearly labelled test action for your agent. Follow the documented key setup; registration alone is not a claim that signing is ready.
4. [Verify the receipt](https://docs.truthlocks.com/api-reference/agent-receipts/verify). Inspect signature and transparency results separately. Use `https://sandbox-api.truthlocks.com/v1` with sandbox credentials; never mix production keys or customer records into the trial.
5. Share your runtime version, passed/failed step and sanitized error in a repository issue. Never publish tokens, passwords, private keys, private receipts or identity documents.

Optional website attribution is consent-based. This offline script collects no telemetry. Running it counts as a local trial, not a hosted product activation. A hosted activation means a real external developer created their own agent and successfully created and verified a receipt, supported by consented evidence.
